# commit

변경사항을 분석하여 컨벤션에 맞게 커밋하는 스킬.

## 절차

### 1. 변경사항 분석
- `git status --short`로 변경 파일 목록(수정/추가/삭제/untracked)을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 읽는다.
- untracked 파일은 내용을 직접 읽어 목적을 파악한다.
- `git log --oneline -10`으로 기존 커밋 스타일을 참고한다. (커밋이 없으면 생략)
- `.env`, 키, 토큰 등 비밀 정보나 빌드 산출물·`node_modules`가 포함돼 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 성격(기능 추가 + 리팩터링 + 설정 변경 등)이 섞여 있으면 분리한다.
- 같은 파일 안에서도 목적이 다르면 `git add -p` 등으로 hunk 단위 분리를 제안한다.
- 분류 결과를 "커밋 N: 포함 파일 / 요약" 형태로 정리한다.

### 3. 커밋 메시지 작성
형식: `타입: 요약`

| 타입 | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 기타 작업 |

규칙:
- 한국어로 작성한다. (기술 용어·식별자는 원문 유지)
- 제목은 50자 내외, 마침표 없이 "무엇을 했는지" 중심으로 쓴다.
- 이유나 맥락이 필요하면 빈 줄 후 본문에 간단히 덧붙인다.
- 예: `feat: 컴포넌트 생성 API 엔드포인트 추가`, `fix: 프리뷰 렌더링 시 빈 props 오류 수정`

### 4. 커밋
- 기본 동작은 **승인 없이 바로 커밋**이다. 분류와 메시지 작성이 끝나면 곧바로 진행한다.
- 사용자가 "확인하고 커밋", "먼저 보여줘" 등을 요청하면 커밋 계획(커밋별 파일 목록 + 메시지)을 보여주고 승인을 받은 뒤 커밋한다.
- 아래 경우에는 승인 여부와 관계없이 먼저 사용자에게 물어본다.
  - 비밀 정보로 의심되는 파일이 포함된 경우
  - 분류가 모호해 어떻게 나눌지 판단하기 어려운 경우
  - 기본 브랜치(main/master)에서 작업 중인 경우
- 커밋별로 필요한 파일만 명시적으로 `git add <파일>` 한 뒤 `git commit`한다. (`git add -A`/`.` 지양)
- 메시지는 HEREDOC으로 전달해 줄바꿈·인코딩 문제를 피한다.
- 시스템 지침에 커밋 attribution 줄이 지정돼 있으면 메시지 끝에 추가한다.
- 완료 후 `git log --oneline -n <커밋 수>`와 `git status`로 결과를 확인하고, 만든 커밋 목록을 사용자에게 보고한다.

## 주의
- 사용자가 요청하지 않는 한 `git push`, `--amend`, `--no-verify`, force 옵션을 쓰지 않는다.
- pre-commit hook이 실패하면 원인을 수정한 뒤 **새 커밋**으로 다시 시도한다.
- 변경사항이 없으면 커밋하지 않고 그렇게 알린다.
