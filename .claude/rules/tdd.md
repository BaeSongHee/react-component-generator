# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트별 규칙이 없을 때 적용되는 **기본값(fallback)** 이다.
- 충돌하는 항목만 프로젝트 규칙을 따르고, 나머지는 이 파일을 유지한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이, 데이터 변환)
- **API** (엔드포인트, 요청/응답 처리, 에러 매핑)
- **유틸 함수** (순수 함수, 파서, 포매터)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다)

### TDD 불필요

- **타입 정의** (`type`, `interface`만 있는 파일)
- **설정 파일** (빌드, 린트, tsconfig 등)
- **순수 UI** (로직 없는 마크업/스타일 변경)
- **SQL** (스키마, 마이그레이션, 쿼리 정의)

판단이 애매하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR 사이클

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행 없이 실패했다고 가정하지 않는다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 설정 오류, 문법 오류로 인한 실패는 RED가 아니다. 먼저 고쳐서 올바른 이유로 실패하게 만든다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 못한다. 테스트를 수정한다.

### 2. GREEN — 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능, 옵션, 분기를 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.
- 기존 테스트가 깨지면 이번 변경이 원인이다. 먼저 해결하고 다음으로 넘어간다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 변경할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 보면서 다시 쓰기 모두 포함한다.
- 삭제 후에는 테스트에서 요구하는 것만 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 쓴다. 단순해 보이는 코드가 가장 자주 조용히 깨진다. 테스트는 그 단순함을 고정한다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰 작성돼 버그까지 통과시킨다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정에 드는 시간이 테스트 작성 시간보다 크다. 급할수록 안전망이 필요하다. |
| "삭제하면 낭비" | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. 테스트 주도로 다시 쓰면 더 작고 정확해진다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라고 확신하면 코드를 버리고, 남길 코드면 TDD를 적용한다. |
